# 学习级电商系统需求与开发计划

## 1. 文档目的

本文档用于指导后端空工程和独立前端工程逐步开发为一个前后端分离的学习级电商系统。开发过程强调“小步实现、小步验证”，每次只完成一个明确目标，避免一次性堆叠多个模块。

本文档是当前需求基线。后续如果需求或技术方案发生变化，应先修改本文档，再修改代码。

## 2. 项目边界

### 2.1 当前项目包含

- Spring Boot REST API 后端。

- 普通用户端所需的后端接口。

- 管理端所需的后端接口。

- MySQL 数据持久化。

- MyBatis-Plus 数据访问。

- Redis 购物车、订单超时队列及后续缓存能力。

- Spring Security + JWT 身份认证和权限控制。

- 订单、库存、模拟支付、发货等核心电商流程。

### 2.2 当前项目不包含

- 前端代码不放在当前 Spring Boot 工程中。用户端和管理端页面将在独立前端工程目录中开发和启动，但开发步骤纳入本文档并与后端任务交错进行。

- Spring Cloud 微服务。第一阶段采用模块化单体，后期再拆分。

- 真实支付、短信验证码、邮件验证码。

- 优惠券、积分、退款、售后、商品评价。

- 多商户、多仓库、秒杀和分布式事务。

- 商品图片文件上传。第一版只保存图片 URL。

- 多规格 SKU。第一版一个 `product` 就是一个可购买、可计库存的商品。

| --------- | ----------------------- | ------------------------------------- |
| 语言        | Java 17                 | 当前工程配置                                |
| 基础框架      | Spring Boot             | 开发前先确认当前 Boot 版本与其他依赖兼容性              |
| Web       | Spring MVC              | 提供 REST API                           |
| 权限        | Spring Security         | 认证、角色授权、当前用户上下文                       |

| 数据库       | MySQL 8.x               | 用户、商品、订单和库存的最终数据源                     |
| 缓存        | Redis                   | 购物车、订单过期 ZSet、幂等令牌、可选缓存               |
| 数据库脚本     | `db/create.sql`         | 集中保存全部建表和初始化 SQL，由开发者手动执行             |
| 参数校验      | Jakarta Validation      | 请求参数声明式校验                             |
| API 文档与调试 | OpenAPI/Swagger         | 展示接口文档，并用于逐个手动调用和验收接口                 |
| 功能验收      | Swagger、MySQL、Redis CLI | 不编写单元测试或集成测试，通过手动调用和数据检查验收            |
| 前端工程      | 独立工程目录                  | 与当前 Spring Boot 工程并列，包含用户端和管理端页面      |
| 前端技术栈     | React、Vite、TypeScript   | React Router、Zustand、Axios、Ant Design |

数据库脚本约定：

- 所有建库、建表、索引和管理员初始化语句统一写在项目根目录的 `db/create.sql`。

- 项目不会在启动时自动执行 SQL，由开发者使用 MySQL 客户端手动执行。

- `db/create.sql` 应保持“针对空数据库可从头完整执行”的状态，并按外键依赖顺序排列语句。

- 表结构发生变化时直接同步维护 `db/create.sql`；学习阶段是否清空并重建本地数据库由开发者自行决定。

HTTP 方法约定：

- 查询操作使用 `GET`。

- 注册、登录、新增、修改、删除和业务动作全部使用 `POST`。

- 本项目不提供 `PUT`、`PATCH` 或 `DELETE` 请求。

## 4. 角色及权限

### 4.1 游客

- 注册普通用户。

- 登录。

- 查询已启用的分类。

- 查询已上架的商品列表和商品详情。

### 4.2 普通用户 `USER`

- 拥有游客的全部能力。

- 管理自己的收货地址。

- 管理自己的购物车。

- 提交订单和模拟付款。

- 查询自己的订单。

- 取消自己的待付款订单。

- 确认收货。

- 不能访问其他用户的数据或管理端接口。

### 4.3 管理员 `ADMIN`

- 管理员账号由初始化 SQL 写入数据库，不能通过接口注册。

- 管理分类、商品和库存。

- 查询系统全部订单。

- 对待发货订单执行发货。

- 管理员密码也必须以 BCrypt 密文保存。

## 5. 核心业务规则

### 5.1 用户与 JWT

- 用户名唯一，建议长度为 4～32 个字符。

- 密码建议长度为 6～64 个字符，数据库只保存 BCrypt 密文。

- 普通用户注册成功后直接返回 JWT，视为自动登录。

- 普通用户登录成功后返回 JWT。

- 管理员使用独立的管理端登录接口。

- JWT 有效期固定为 7 天。

- JWT 至少包含用户 ID、角色、签发时间和过期时间。

- 后端从认证上下文获取当前用户 ID，不能相信前端提交的用户 ID。

- 第一版可不实现刷新令牌；退出登录黑名单作为增强项。

### 5.2 商品分类

- 第一版只实现一级分类。

- 分类名称不能重复。

- 分类具有启用、停用状态和排序值。

- 用户端只显示已启用分类。

- 分类下存在未删除商品时，不允许直接删除分类。

- 删除分类采用逻辑删除。

### 5.3 商品

- 数据库和代码统一使用名称 `product`，不与 `goods` 混用。

- 商品状态为 `DRAFT`、`ON_SALE`、`OFF_SALE`。

- 用户端只显示未删除且状态为 `ON_SALE` 的商品。

- 商品价格必须大于等于 0，使用 `DECIMAL` 和 Java `BigDecimal`。

- 商品库存必须大于等于 0。

- 删除商品采用逻辑删除；历史订单不受商品修改或删除影响。

- 上架商品必须拥有有效分类、名称、价格和非负库存。

- 第一版不实现 SKU，一个商品只有一个价格和一个库存数量。

### 5.4 收货地址

- 地址只能由所属用户读取和修改。

- 一个用户可以拥有多个地址，但最多只有一个默认地址。

- 设置新默认地址时，应取消原默认地址。

- 下单时复制地址快照；用户后续修改地址不会影响历史订单。

### 5.5 购物车

- 购物车只允许登录用户使用。

- 购物车主体保存在 Redis，建议使用 `cart:{userId}` Hash。

- 同一商品重复加入购物车时累加数量。

- 单种商品数量范围暂定为 1～99。

- 购物车保存商品 ID、数量和选中状态，不把购物车价格视为成交价格。

- 查询购物车时展示商品当前名称、价格、状态和库存。

- 商品下架、删除或库存不足时，应显示失效原因且不允许结算。

- 创建订单时必须重新查询 MySQL 中的价格、状态和库存。

### 5.6 订单与库存

- 订单状态：`PENDING_PAYMENT`、`PENDING_SHIPMENT`、`SHIPPED`、`COMPLETED`、`CANCELED`。

- 创建订单时由后端计算单价、小计和总金额，不能采用前端提供的最终金额。

- 创建订单时扣减库存，以便在 20 分钟付款窗口内占用库存。

- 库存扣减使用带库存条件的 SQL，避免超卖。

- 多件商品中任意一件库存不足时，整个下单事务回滚。

- 订单明细保存商品名称、图片、单价等下单快照。

- 新订单默认为待付款状态，过期时间为创建时间加 20 分钟。

- 待付款订单可由用户主动取消；取消后恢复库存。

- 待付款订单超过 20 分钟自动取消；取消后恢复库存。

- 已付款订单不能被取消任务再次取消或恢复库存。

- 支付、取消、库存恢复和发货都必须设计为幂等操作。

### 5.7 模拟支付和发货

- 本项目不调用第三方支付平台。

- 用户调用模拟支付接口后，订单从待付款变为待发货。

- 已过期、已取消或非本人的订单不能支付。

- 管理员只能对待发货订单执行发货。

- 发货后订单进入已发货状态，并保存发货时间、快递公司和快递单号。

- 用户只能对自己的已发货订单确认收货，之后订单进入已完成状态。

### 5.8 超时订单实现

- Redis ZSet 保存待付款订单，key 暂定为 `order:payment:timeout`。

- ZSet member 为订单号或订单 ID，score 为订单过期时间戳。

- Spring 定时任务周期性读取已到期订单并尝试取消。

- MySQL 是订单状态的最终依据，取消时必须使用条件更新或锁处理并发。

- 增加 MySQL 补偿扫描，处理 Redis 重启、写入失败或数据丢失。

- 查询订单和模拟支付时也应检查订单是否已超过付款期限。

## 6. 主要数据表

| 表名                  | 主要用途     | 关键字段示例                                                               |
| ------------------- | -------- | -------------------------------------------------------------------- |
| `user`              | 普通用户和管理员 | `id`、`username`、`password`、`nickname`、`role`、`status`                |

## 8. 从 0 到 1 开发规划

说明：每完成一行都应运行或手动执行对应验收，确认通过后再进入下一行。`状态` 初始统一为“未开始”，后续学习过程中可以修改为“进行中”或“已完成”。后端任务沿用三位数字编号，新增的前端与联调任务使用 `F` 前缀，并穿插在对应后端能力之后。

每个功能默认遵循以下开发节奏：

1. 设计并创建数据库结构。
2. 完成后端实体、Mapper、Service 和接口。
3. 使用 Swagger 验证后端接口。
4. 封装对应前端 API。
5. 开发页面并进行真实前后端联调。
6. 当前功能前后端都验收通过后，再开始下一个业务模块。

例如管理员登录的顺序是：创建用户表 → 写入初始化管理员 → 完成管理员登录接口 → Swagger 验证 → 开发管理端登录页面 → 联调并进入管理首页。

## 9. 每一步推荐学习节奏

每个表格任务建议都按以下循环完成：

1. 先阅读对应概念，例如逻辑删除、JWT 过滤器或条件更新。
2. 只实现当前一行，不提前把后续模块全部生成出来。
3. 使用 Swagger、MySQL 客户端或 Redis CLI 手动验证当前结果。
4. 记录遇到的问题以及为什么采用当前实现。
5. 当前任务验收通过后，把状态改成“已完成”，再进入下一行。

## 10. 第一阶段完成标准

满足以下条件时，可以认为前后端分离的学习级电商系统从 0 到 1 完成：

- 普通用户能够注册、登录并持有 7 天有效 JWT。

- 管理员能够登录，但不能通过接口注册。

- 管理员能够管理分类、商品和库存。

- 游客能够浏览分类和上架商品。

- 用户能够维护收货地址和 Redis 购物车。

- 用户能够创建订单，且并发场景不会超卖。

- 待付款订单能够模拟支付或在 20 分钟后自动取消。

- 取消订单只恢复一次库存。

- 管理员能够查询订单并发货。

- 用户能够查询自己的订单并确认收货。

- 用户端页面能够完成注册、登录、浏览商品、管理地址、管理购物车和完整订单流程。

- 管理端页面能够完成管理员登录、分类管理、商品管理、库存调整、订单查询和发货。

- 前端能够统一携带 JWT，并正确处理 401、403、业务错误和登录过期。

- 前后端开发环境可分别启动并正常联调，所有 HTTP 请求只使用 GET 和 POST。

- 关键权限、事务、幂等和状态流转均已按照手动验收清单验证。

- 后端具备完整 Swagger 接口文档，前后端均具备本地运行说明。
